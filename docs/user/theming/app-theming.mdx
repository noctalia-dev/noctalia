Noctalia can render the resolved theme colors into external app config files whenever the palette changes. This lets terminals, editors, browsers, launchers, and other apps follow the same colors as the shell.

Templates always render the variant selected by [`[theme].mode`](/noctalia/theming/#mode), never
[`shell_mode`](/noctalia/theming/#shell_mode), so pinning Noctalia to dark keeps your apps on whatever `mode` resolves to.

To rerender enabled templates for the current palette without changing the theme, use
[Media & UI → Theme](/noctalia/ipc/media-and-ui/#theme).

## Built-in Templates

Built-in templates ship with Noctalia. Enable the built-in catalog, then opt in to the template IDs you want:

```toml
[theme.templates]
enable_builtin_templates = true
builtin_ids              = []        # opt-in; run: noctalia theme --list-templates
```

`builtin_ids` selects which shipped templates run. An empty array means no built-in templates are applied.

In **Settings → Templates**, click a built-in template's external-link button (tooltip: **Documentation**) to open its setup guide in your default browser. Opening the guide does not enable or disable the template.

Hover highlights the external-link button separately from its template tile, including on enabled templates.
The entry stays highlighted while the pointer is over its link button, with a continuous highlight when moving between them.
The link glyph follows the tile's text color when hovering or pressing the surrounding entry.
Link tooltips are positioned at the link button rather than the center of the tile.

Disabling a built-in template removes its generated Noctalia theme file and undoes any Noctalia-owned include or theme
selection that the template added to the application's config. Disabling `enable_builtin_templates` performs the same
cleanup for every selected built-in template.

Application configs must be writable for Noctalia to remove those integrations. For declaratively managed configs such
as Home Manager symlinks into the Nix store, remove the Noctalia include or theme selection from the declarative source.

For Alacritty, foot, and kitty, the built-in template can create a user config that includes the Noctalia theme.
These applications stop reading their other config locations once a user config exists, so the template skips this
step and logs a warning when another config is present, for example `/etc/xdg/foot/foot.ini` written by the NixOS
`programs.foot.settings` option. Add the include named in the warning to that config to apply the Noctalia theme.

List available built-in and configured template IDs:

```sh
noctalia theme --list-templates
```

### Compositor Configuration

Compositor templates generate their theme files and automatically add an include or theme selection to an existing,
writable user config. They never create a missing primary compositor config: doing so could hide the system,
packaged, or custom config that your compositor currently uses.

If the primary user config is absent, the generated theme is still available. A dismissible banner in Settings
explains the problem and the manual setup. Long messages scroll inside the banner.
The instructions are also logged, including when Settings is closed.
Add the include or theme selection to the config your compositor actually loads, then reapply the template to
retry. For a read-only or declaratively managed config, make that change in its source, such as your Home Manager
configuration.

The examples below use the default config directory and an example home directory. Replace `/home/you/.config`
with your resolved `$XDG_CONFIG_HOME`, or `$HOME/.config` when it is unset. Config files do not necessarily expand
environment variables; use the resolved path. Absolute paths also avoid resolving an include beside a system or
custom config instead of beside the generated theme.

| Compositor | Primary user config, relative to the config directory | Generated theme, relative to the config directory | Manual integration |
| --- | --- | --- | --- |
| Umbriel | `umbriel/config.toml` | `umbriel/noctalia.toml` | Add the path to `[include.optional].files`, as shown below. |
| Niri | `niri/config.kdl` | `niri/noctalia.kdl` | `include "/home/you/.config/niri/noctalia.kdl"` |
| Sway | `sway/config` | `sway/noctalia` | `include "/home/you/.config/sway/noctalia"` |
| Scroll | `scroll/config` | `scroll/noctalia` | `include "/home/you/.config/scroll/noctalia"` |
| Mango | `mango/config.conf` | `mango/noctalia.conf` | `source=/home/you/.config/mango/noctalia.conf` |
| Hyprland (Hyprlang) | `hypr/hyprland.conf` | `hypr/noctalia.conf` | `source = /home/you/.config/hypr/noctalia.conf` |
| Hyprland (Lua) | `hypr/hyprland.lua` | `hypr/noctalia.lua` | `dofile("/home/you/.config/hypr/noctalia.lua").apply_theme()` |
| Labwc | `labwc/rc.xml` | `labwc/noctalia.conf` | Select the `noctalia` theme as shown below. |

For Umbriel, append the generated path to the existing `files` array, or add this section if it is absent:

```toml
[include.optional]
files = ["/home/you/.config/umbriel/noctalia.toml"]
```

For Labwc, the template also installs the theme in
`${XDG_DATA_HOME:-$HOME/.local/share}/themes/noctalia/openbox-3/themerc`. Set the name inside the existing
`<theme>` element, or add this element inside `<labwc_config>`:

```xml
<theme>
  <name>noctalia</name>
</theme>
```

If an earlier Noctalia version created a primary config containing only its theme integration, inspect that file
before moving it aside manually. Moving it aside lets the compositor discover its previous config again. Preserve
any settings you added, then add the theme integration to the config you intend to use. Noctalia does not delete
primary configs automatically.

## Community Templates

Community templates are fetched from `https://api.noctalia.dev/templates` and cached locally:

```toml
[theme.templates]
enable_community_templates = true
community_ids              = []        # opt-in; fetched from api.noctalia.dev/templates
```

`community_ids` selects which community templates run. In **Settings → Templates**, enable community templates and use **Browse Templates** to search and filter the catalog (by category or enabled-only). Metadata and files are stored in `~/.local/state/noctalia/community-templates/` (honoring `NOCTALIA_STATE_HOME`, then `XDG_STATE_HOME`).

Some community templates include extra setup instructions in a `README.md` in the [community-templates repository](https://github.com/noctalia-dev/community-templates). Their tiles show an external-link button with the **Readme** tooltip; click it to open those instructions in your default browser without changing the template's enabled state. With a template selected in the catalog grid, **F1** opens its README. READMEs are optional, so templates without one have no external-link button.

Cached community template files are treated as editable local copies. Sync updates files only while their content still matches the last Noctalia-written md5; local edits are preserved until you delete the edited cached file.

Disabling a community template, or disabling `enable_community_templates`, runs the `undo_hook` of each entry in its
cached `template.toml`, so the template can remove an include or theme selection its `post_hook` added. A failed undo
hook is retried on the next theme application. Templates without an `undo_hook` leave their files in place.

Community template discovery and updates require network access unless the selected template is already cached. [`shell.offline_mode`](/noctalia/configuration/shell/#shell-settings) prevents outgoing HTTP requests, including community template requests.

## User Templates

User templates are declared directly in Noctalia config:

```toml
[theme.templates.user.my_app]
input_path  = "$XDG_CONFIG_HOME/noctalia/templates/my-app.css"
output_path = "$XDG_CONFIG_HOME/my-app/theme.css"
post_hook   = "my-app --reload-theme"
```

Defining `[theme.templates.user.<id>]` enables that user template. Set `enabled = false` on an entry to keep it available but inactive.

Relative paths resolve from the Noctalia config directory. A leading `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME`, `$XDG_STATE_HOME`, or `$XDG_CACHE_HOME` token is expanded using the XDG base directory defaults when the matching environment variable is not set.

User template entries support the same fields documented in [Template Entries](/noctalia/theming/templates/#template-entries), including `input_path_modes`, `output_path_dynamic`, `colors_to_compare`, `compare_to`, `pre_hook`, `post_hook`, `post_action`, and `index`.

## Config Location

Put dotfile-managed templates in `~/.config/noctalia/*.toml`:

```toml
# ~/.config/noctalia/templates.toml
[theme.templates]
enable_builtin_templates   = true
enable_community_templates = true
builtin_ids                = []
community_ids              = []

[theme.templates.user.my_app]
input_path  = "$XDG_CONFIG_HOME/noctalia/templates/my-app.css"
output_path = "$XDG_CONFIG_HOME/my-app/theme.css"
```

The same tables are valid in `settings.toml` because it is the final config overlay, but that file is managed by the GUI and runtime actions. Use `~/.config/noctalia/` for templates you want to keep in dotfiles.
